Define your application data model once.

ModelSpec is an open specification language for application data models. It describes the logical model of an application independently of storage engines, programming languages, API layers and deployment platforms — so a schema, a contract and a type become projections of your model rather than four places your model lives.

01 — The problem

Every application defines the same model again and again.

03 — Core concepts

A small, honest vocabulary.

Record types are named structures of typed fields, with an optional key. Components are reusable groups of fields. Enums are named vocabularies. A reference says that a field refers to another record type.

Record type

A named structure of typed fields — User, Order, Invoice. A key is optional: without one, the model makes no claim of record identity.

record "User" {
  key = ["id"]

  field "id" {
    type = "uuid"
  }
}

Component

A reusable group of fields with no independent identity — composition over inheritance.

component "Auditable" {
  field "createdAt" {
    type     = "datetime"
    required = true
  }
}

Composition

Record types use components, much like Go struct embedding — no deep type hierarchies.

record "Invoice" {
  key = ["id"]
  use = ["Auditable"]

  field "id" {
    type = "uuid"
  }
}

Reference

A field that refers to another record type. It is true whether or not a database declares a foreign key for it.

field "user" {
  record   = "User"
  required = true
}

04 — A complete example

One model, one file, no storage engine chosen yet.

ModelSpec is authored in HCL. Tooling parses it into an AST, which is then serialized to JSON for machine ingestion.

model.hcl
component "Auditable" {
  field "createdAt" {
    type     = "datetime"
    required = true
  }

  field "updatedAt" {
    type     = "datetime"
    required = true
  }
}

record "User" {
  key = ["id"]
  use = ["Auditable"]

  field "id" {
    type = "uuid"
  }

  field "email" {
    type     = "string"
    required = true
    unique   = true
    format   = "email"
  }
}

record "Order" {
  key = ["id"]

  field "id" {
    type = "uuid"
  }

  field "user" {
    record   = "User"
    required = true
  }
}

The same logical model — User → Orders → OrderItems — can become a nested Firestore path or three flat PostgreSQL tables without the model definition changing. No generator does this yet. Models can also reference concepts in other modules by qualified name, so a shared vocabulary can be defined once and reused.

Earlier drafts wrote a record type as entity and its fields as property. The tools that read ModelSpec files, the reference CLI and the public registry's check among them, accept both, and modelspec rewrite --write converts a file.

05 — Consumers

An independent specification, with real consumers.

ModelSpec is maintained under the SpecScore GitHub organisation, but it is independent: any project can adopt it without adopting SpecScore, OpenVaultDB, GraphSpec, or any particular backend.

OpenVaultDB

Says where the data is. A database in the OVDB Directory names the model it follows, and ovdb publisher check verifies its recordsets against that model. A vault that validates writes, plans migrations or maps a backend from a model is planned; no code does it today. openvaultdb.com ↗

GraphSpec

A consumer, not a parent. GraphSpec references ModelSpec record types, components and enums rather than defining structure itself. ModelSpec never references GraphSpec.

SpecScore

Validates ModelSpec but does not own its semantics — linting, structural validation and semantic checks over ModelSpec documents. specscore.md ↗

Generators

Generator targets named by the specification — GraphQL, Go, TypeScript, SQLite, PostgreSQL, Firestore, inGitDB and OpenVaultDB schemas. Planned; none are implemented yet.

06 — Scope

What ModelSpec defines, and what it deliberately doesn't.

A specification is as useful as its boundaries are clear.

Defines

  • Record types
  • Fields
  • Keys
  • References
  • Reusable components
  • Named enumerations
  • Constraints

The words projection, index and migration are reserved and have no content yet.

Does not define

  • RBAC or permissions
  • OAuth or identity flows
  • Feature specifications
  • Workflows
  • Deployment topology
  • UI behaviour

Those belong to adjacent specifications and to application architecture.

07 — Status

Preview. The specification is still moving.

ModelSpec is in early specification development, published as a preview so it can be read and argued with. The grammar and vocabulary may change before ModelSpec v1.0, and no generator has been implemented yet — the value proposition is specified, not yet executed.

Honest status
  • Specification — active
  • HCL authoring grammar — drafted
  • JSON serialization — first machine format
  • JSON Schema — published
  • YAML serialization — out of scope for v0
  • Generators — planned, none built
  • Reference CLI and its test corpus — released

Decisions are recorded in the open, in the repository, and superseded ones are kept rather than rewritten.

Registry — new, draft

Where it is, what shape it has, what it means.

One database can be described by three layers, each answering one question. ModelSpec is the middle one, and the model registry is its public list of published models. The registry is new and still a draft.

ModelSpec

The shape of the data (record types, fields, types and links), written once, whatever stores it. Browse the models

OVDB Directory

Where the data is, who publishes it and how to reach it. directory.openvaultdb.com ↗

MeaningGraph

What the data means. Meanings are attached to ModelSpec fields, so one description serves every copy of the same model. meaninggraph.io ↗

Chinook is in all three: listed in the OVDB Directory, modelled in ModelSpec, explained in MeaningGraph.

Why a shared model helps

  • Start from a published model. A new project can reuse a model someone has already written and checked, instead of designing its tables again.
  • Recognise the same data in different places. When several hosters serve databases built on the same model, tools can tell they share one shape and treat them alike.
  • Run many databases of one model. A service that gives every customer an isolated database can declare one model for all of them.

Read it, and tell us where it's wrong.
